# Contract Deployment Records

This directory stores generated metadata for xConfess Soroban contract builds
and network deployments.

## Files

- `contract-wasm-manifest.json` is generated by
  `./scripts/contracts-release.sh build`. It records release WASM paths,
  crate versions, byte sizes, and SHA-256 hashes before deployment.
- `<network>.json` is generated by
  `./scripts/contracts-release.sh deploy --network <network> --source <key>`.
  Use the Stellar CLI network alias as the filename, for example
  `deployments/testnet.json` or `deployments/public.json`.
- `sample.redacted.json` is an example only. It documents the expected shape
  without real contract IDs or deployer information.
- `rollback-evidence/<network>.json` is the rollback evidence archive for
  application and schema rollback drills. See
  [Rollback Evidence Archive](#rollback-evidence-archive).

## Naming Convention

Deployment metadata must use:

```text
deployments/<network>.json
```

`<network>` must match the network argument passed to the release script. If the
team uses `public` as the Stellar CLI alias for mainnet, commit
`deployments/public.json`. If the team explicitly configures a `mainnet` alias,
commit `deployments/mainnet.json` and mention the alias in the release notes.

## Signed Contract Release Manifest

`contract-release-manifest-<network>-<revision>.json` binds each release's
WASM SHA-256, ABI SHA-256 and version, full source revision, and network alias,
network id, environment, and Stellar passphrase. The manifest is signed with
Ed25519 over canonical JSON. The signature key id is checked against the
independently configured trusted public key; the public key in a manifest is
never trusted by itself.

The deploy command creates and verifies this manifest after artifact checks
and before invoking Stellar. A missing signing key, missing trusted key,
signature failure, source/network mismatch, ABI-version mismatch, unsafe or
missing artifact path, or artifact digest mismatch aborts deployment. The
manifest is immutable for a given network and source revision; rerunning the
same operation reuses an existing manifest only after verifying it again.
After a successful deployment, `<network>.json` records the release-manifest
path, digest, and source revision so deployment metadata remains linked to the
signed candidate.

Configure `XCONFESS_RELEASE_SIGNING_KEY` (Ed25519 private-key PEM) only in the
release operator's secret store, and configure its matching
`XCONFESS_RELEASE_TRUSTED_PUBLIC_KEY` (public-key PEM) in the verifier
environment. Never commit either key. Rotate by distributing the new trusted
public key to all verifiers before signing with the corresponding private
key. Standard `testnet`, `futurenet`, `mainnet`, `public`, and `pubnet` aliases
have network metadata defaults. Custom aliases additionally require
`XCONFESS_NETWORK_ID`, `XCONFESS_RELEASE_ENVIRONMENT`, and
`XCONFESS_NETWORK_PASSPHRASE`.

To verify a generated release again:

```bash
node scripts/contract-release-manifest.js verify \
  --network testnet \
  --manifest deployments/contract-release-manifest-testnet-<full-revision>.json
```

Verification checks the trusted signature and re-hashes the local WASM and
ABI artifacts. Consumers at the release boundary must reject failed
verification; they must not fall back to unsigned contract IDs.

### Committed metadata gate

Run the repository-wide manifest gate before merging deployment or ABI changes:

```bash
npm run contracts:validate-manifests
```

The gate validates all committed ABI/WASM manifests, deployment records, and
fixture snapshots. It fails when:

- networks or network passphrases disagree across metadata;
- a contract set, contract ID, version, WASM digest, or ABI digest drifts;
- a deployed or snapshotted contract ID is not a valid Stellar contract ID;
- a deployment record is missing `network`, `environment`, `target`,
  `generated_at_utc`, or required contract fields; or
- a recorded ABI digest does not match the committed ABI artifact.

This validation is a release gate, not a runtime fallback. Invalid or missing
metadata must be corrected and retried; consumers must not silently substitute
an unverified contract ID.

## Rollback Evidence Archive

Rollback drills for both application deploys and schema migrations must leave
an auditable record at the owning release boundary. Evidence is written to
`deployments/rollback-evidence/<network>.json` and is consumed by the release
compatibility check (`npm run check:release-compatibility`) and the artifact
secret scan (`npm run secret-scan:artifacts`).

### Record Shape

Each archive file is a JSON object:

```json
{
  "network": "testnet",
  "environment": "staging",
  "retention_days": 90,
  "drills": [
    {
      "id": "app-rollback-2024-06-01",
      "kind": "application",
      "started_at": "2024-06-01T10:00:00Z",
      "duration_seconds": 420,
      "inputs": { "from_version": "1.4.2", "to_version": "1.4.1" },
      "decision_points": [
        { "at": "2024-06-01T10:02:00Z", "decision": "proceed", "reason": "health checks green" }
      ],
      "outcome": "success",
      "notes": "rolled back to previous release"
    },
    {
      "id": "schema-rollback-2024-06-02",
      "kind": "schema",
      "started_at": "2024-06-02T09:00:00Z",
      "duration_seconds": 610,
      "inputs": { "migration": "20240602_add_index", "direction": "down" },
      "decision_points": [
        { "at": "2024-06-02T09:05:00Z", "decision": "abort", "reason": "lock contention" }
      ],
      "outcome": "failed",
      "retry_of": "schema-rollback-2024-06-01",
      "notes": "retried after clearing locks"
    }
  ]
}
```

### Sanitization

Drill inputs and decision points must be sanitized before archiving. Do not
store raw secrets, tokens, connection strings, or unsanitized request/response
payloads. Only record the fields needed to reconstruct the decision trail
(versions, migration names, direction, timestamps, and short reasons). The
`secret-scan:artifacts` check fails the release if a committed evidence file
contains credential-shaped values.

### Retention

`retention_days` is required and must be a positive integer. Evidence older
than `retention_days` (measured from `started_at`) is pruned by the release
compatibility check; archives that exceed retention without pruning fail
`check:release-compatibility`. Production archives must use a retention of at
least 90 days.

### Access Controls

- Writing evidence requires the release/deploy role; the archive is not
  writable by application runtime credentials.
- Reading evidence is limited to release engineers and on-call responders.
- Evidence files are committed only for shared environments; local drill
  records stay out of the repository.

### Success, Validation, and Failure Semantics

- **Success**: a drill record with `outcome: "success"` and at least one
  decision point is accepted and retained.
- **Validation**: records missing `id`, `kind` (`application` or `schema`),
  `started_at`, `duration_seconds`, `outcome`, or `retention_days` are
  rejected by `check:release-compatibility`.
- **Failure/retry**: a drill with `outcome: "failed"` must include a `retry_of`
  reference to the prior attempt (or `null` for the first attempt) so retries
  are traceable. Failed drills are retained like successful ones.

## What To Commit

Commit:

- reviewed `deployments/<network>.json` files for shared environments
- `deployments/contract-wasm-manifest.json` when publishing a release artifact
  snapshot for review
- sanitized `deployments/rollback-evidence/<network>.json` archives for shared
  environments
- documentation examples such as `sample.redacted.json`

Do not commit:

- private keys, secret keys, seed phrases, or local `.env` files
- one-off local deployment records from personal experiments
- generated build directories such as `xconfess-contracts/target/`
- unreviewed metadata where hash changes cannot be traced to source changes
- unsanitized rollback evidence containing secrets or raw payloads

Before committing a deployment file, verify the hashes with the checksum
workflow in `docs/contract-release-and-upgrade-runbook.md`.

## Updating Shared Metadata After Redeploy

After redeploying shared contracts, update metadata and service env vars from
the same deployment output:

```bash
./scripts/contracts-release.sh deploy --network testnet --source "$DEPLOYER_KEY"
jq -r '.contracts | to_entries[] | [.key, .value.contract_id] | @tsv' deployments/testnet.json
```

Map the public IDs into environment configuration:

- `confession-anchor` -> `CONFESSION_ANCHOR_CONTRACT_ID`
- `reputation-badges` -> `REPUTATION_BADGES_CONTRACT_ID`
- `anonymous-tipping` -> `TIPPING_SYSTEM_CONTRACT_ID`

Then run:

```bash
npm run contracts:verify-env
```

Commit `deployments/testnet.json` in the same change that updates CI,
Render/Vercel, or environment templates. CI preflight uses this command with
`DEPLOYMENT_METADATA_PATH=deployments/testnet.json`, so stale env vars fail
before deploy.
